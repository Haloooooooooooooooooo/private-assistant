这份文档专门记录本项目的 Agent 系统是如何从 0 到 1 搭建起来的，包括：

1. 我们为什么这样设计
2. 每个阶段具体做了什么

---

## 2. 一句话定义这个项目

我们做的是一个 `Workflow-Orchestrated Multi-Agent` 的个人知识内化系统：

1. 用户先收录内容（文字/链接/图片/文档）
2. 系统完成轻解析
3. 用户一键内化
4. 多角色 Agent 自动生成可复用笔记并搭建知识结构
5. AI 助手仅基于已沉淀知识进行有来源问答

---

## 3. 总体架构（先讲清大图）

### 3.1 架构原则

1. 固定、可规则化步骤交给 Workflow。
2. 复杂语义理解与生成交给 Agent。
3. 状态推进与关键落库只允许 Workflow 执行。

### 3.2 角色分工

1. `CaptureParsingAgent`：轻语义解析（标题/摘要/标签）。
2. `InternalizationAgent`：生成正式可复用笔记。
3. `StructureAgent`：主题/子主题归类与关联关系。
4. `EvidenceQnAAgent`：证据化问答、来源与不确定性输出。
5. `Workflow Orchestrator`：调度、路由、超时、重试、日志、落库。

### 3.3 技术栈

1. 前端：Next.js + TypeScript
2. 后端：FastAPI
3. 数据层：Supabase Auth + Postgres + Storage
4. 检索：pgvector（仅 `note_chunks` 向量化）
5. 异步：Postgres jobs + worker

## 5. 关键决策清单（面试重点）

### 决策 1：为什么不是单 Agent？

结论：

- 采用多角色 Agent + Workflow 编排。

原因：

1. 单 Agent 容易职责混乱，难以调试和评估。
2. 本项目存在大量确定性步骤，没必要都让 LLM 决策。
3. 多角色有利于独立优化和问题定位。

### 决策 2：为什么一键内化不走人工草稿审核？

结论：

- 内化直接完成，用户后编辑。

原因：

1. 降低用户操作与理解成本。
2. 保持“轻操作”产品体验。
3. 通过后编辑机制补充控制。

### 决策 3：为什么用户不能编辑结构？

结论：

- V1 结构由 Agent 自动维护。

原因：

1. 结构维护是高负担任务，不适合普通用户频繁手动操作。
2. 用户编辑内容、系统维护结构，职责更清晰。

### 决策 4：为什么 AI 助手只基于已沉淀知识？

结论：

- 禁止直接基于未内化收录回答。

原因：

1. 提高可信度与一致性。
2. 避免把临时材料当成稳定知识。

### 决策 5：为什么删除是硬删除且二次确认？

结论：

- 硬删除 + 二次确认 + 级联清理。

原因：

1. 用户预期明确（删了就是删了）。
2. 避免“看似删除但数据残留”。
3. 二次确认降低误操作风险。

## 6. 典型困难与解法（持续补充）

> 这一节是项目最有价值的成长区。每遇到问题就按模板追加一条。

记录模板：

```text
### Case-XXX：<问题标题>
- 现象：
- 根因：
- 方案：
- 权衡：
- 结果：
- 复盘：
```

### Case-001：文档过多且互相冲突

- 现象：新需求讨论时，不同文档给出不一致指引，导致方向摇摆。
- 根因：缺少单一主文档和决策归档机制。
- 方案：收敛为单文档主规范（PRD+开发蓝图），旧文档降级为参考。
- 权衡：短期需要整理成本，长期降低沟通成本和实现偏差。
- 结果：团队对齐速度明显提升。
- 复盘：先治理文档，再开发功能，效率更高。

### Case-002：原型可演示但不具备工程可维护性

- 现象：`background-base.html` 能展示流程，但数据、样式、逻辑耦合在同一文件。
- 根因：原型阶段追求快速验证，不是工程化目标。
- 方案：保留其为 UI 参考基线，迁移到 Next.js 组件化工程。
- 权衡：迁移期工作量增加，但换来长期可维护性。
- 结果：可在不丢交互的前提下接入真实后端。
- 复盘：原型不是废物，是迁移蓝图。

### Case-003：单 Agent 方案讨论时出现能力边界焦虑

- 现象：担心单 Agent 对复杂任务表现不稳定。
- 根因：职责混合导致可控性低，难观测。
- 方案：采用 Workflow 编排的多角色 Agent。
- 权衡：初期设计复杂度略升，但可控性和可演进性更强。
- 结果：职责边界清晰，可按 Agent 单独优化。
- 复盘：复杂系统先拆职责，再谈模型能力。

### Case-004：Phase 1 UI 迁移出现“工程化理解”和“原型等价”偏差

- 现象：前端虽然迁移进了 Next.js，但页面布局和原型不一致，用户明确要求必须一模一样。
- 根因：把“原型迁移”误理解成“允许在原型基础上做工程化再设计”，没有把验收口径钉死在“原型等价”。
- 方案：立即切回“原型直出”承载模式，让首页直接承载 `background-base.html`，同时更新主文档，把 Phase 1 的 UI 约束写死为 1:1 一致。
- 权衡：短期放弃了部分可见的组件化成果，但换来了零偏差的视觉结果，也避免后续继续围绕错误界面开发。
- 结果：前端重新回到用户认可的视觉基线，Phase 2 可以在不破坏页面呈现的前提下继续推进。
- 复盘：只要用户把“和原型一模一样”说清楚，就不能再自行解释成“差不多就行”。

### Case-005：前端真实化阶段的改动权限需要提前定规则

- 现象：Phase 2 以后前端不可避免要为了真实数据接线调整按钮、字段和提示信息，如果权限边界不提前写清，后续很容易再次返工。
- 根因：此前只定义了 Phase 1 的原型等价规则，没有明确 Phase 2 以后哪些前端细节可以动、哪些必须先确认。
- 方案：把规则升级为“两层约束”：整体布局骨架保持不变；所有影响用户可见细节的前端改动都必须先征求用户同意。
- 权衡：会减慢一部分前端实现速度，但能显著降低信任损耗和 UI 回滚成本。
- 结果：后续可以放心先推进后端和数据层，再按用户授权收口前端细节。
- 复盘：改动权限本身也是工程约束，必须像数据模型一样写进主文档和 build playbook。

### Case-006：在没有真实 Supabase 凭证的情况下先推进 Phase 2

- 现象：Phase 2 需要做 `records / attachments / jobs / processing_logs` 真实化，但当前本地还没有可用的 Supabase URL 和密钥，无法直接打云端环境。
- 根因：基础设施配置尚未补齐，但研发节奏不能因此停住。
- 方案：先把数据库表结构 SQL、后端 `records` API 契约、Supabase REST 封装和失败语义做完整；未配置时统一返回 `503`，把缺少环境变量视为明确的可诊断状态，而不是让逻辑静默失败。
- 权衡：这一步无法完成真云验证，但能先把领域模型、接口边界和错误处理固定下来，减少后续接线时的不确定性。
- 结果：Phase 2 已进入“真实化底座就绪”状态，下一步只要补齐 Supabase 配置，就能开始真实落库验证。
- 复盘：当外部依赖还没到位时，优先把契约、表结构和失败语义做扎实，能明显降低后续联调压力。

### Case-007：附件上传和处理日志不先打通，会拖慢 Phase 2 联调

- 现象：仅有 `records` 读写接口还不够，前端真实化还需要附件上传入口和处理日志可观测入口，否则接线会被迫二次返工。
- 根因：之前只完成了记录主表的 API，没有把“上传路径”和“任务日志路径”一起纳入同一批次的后端能力。
- 方案：补齐 `POST /api/records/attachments/upload-ticket`（签名上传票据）和 `GET /api/records/{record_id}/logs`（处理日志查询），同时在创建记录时自动入队 `parse` 任务并写入一条 `processing_logs`。
- 权衡：服务层复杂度上升了一点，但 Phase 2 真实化链路从“单点可用”升级为“端到端可接”。
- 结果：当前后端已具备 `records + attachments ticket + logs` 三条联调通道；未配置 Supabase 时保持一致的 `503` 诊断语义。
- 复盘：数据真实化要按“最小闭环”补能力，不要只补最显眼的一张表。

## 8. 面试讲述模板（可直接背）

### 8.1 30 秒版本

我做了一个个人知识内化 Agent 系统，核心是 `Workflow-Orchestrated Multi-Agent`。  
Workflow 管固定流程和状态落库，四个 Agent 分别处理轻解析、笔记生成、结构归类和证据问答。  
最终实现了从收录到沉淀再到复用的闭环，并通过来源引用和不确定性策略保证回答可信度。

### 8.2 2 分钟版本

我先把项目从“原型能演示”推进到“系统可落地”。最开始只有一个 HTML 原型，我先做了文档治理，收敛成单一主文档和决策清单，避免需求漂移。  
架构上我没有用单 Agent，而是采用 Workflow 编排多 Agent：Workflow 负责状态机、任务、重试、落库，Agent 负责语义理解。  
具体拆成四个角色：CaptureParsing、Internalization、Structure、EvidenceQnA。  
在产品层面，我把用户路径压到最短：收录后轻解析，一键内化直接沉淀，用户可编辑笔记但不维护结构。  
在可信性上，我强制 AI 只用已沉淀知识回答，必须带来源，证据不足明确不确定。  
这套设计让系统既可控又能持续演进，后续只要替换或优化某个 Agent，不会影响整体流程稳定性。

### 8.3 被追问时可展开的 5 个点

1. 为什么多 Agent 而不是单 Agent
2. 为什么 Workflow 必须控制状态与落库
3. 一键内化为什么取消人工审核
4. 如何处理证据不足与错误答案风险
5. 如何保证删除一致性与可观测性
