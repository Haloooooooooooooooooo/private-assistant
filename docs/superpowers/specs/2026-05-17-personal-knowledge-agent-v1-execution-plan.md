## 1. 执行目标

本计划用于指导“个人知识内化 Agent”V1 的整体落地。核心目标不是堆叠功能，而是在可控周期内建立一个可持续运转、可验证质量、可继续演进的产品闭环。

V1 目标如下：

1. 在 6-8 周内交付可用版本，跑通从收录到沉淀再到复用的主路径。
2. 优先保证“可用、可信、可追溯”，再逐步增强“自动化与智能性”。
3. 所有 AI 环节必须具备证据引用、状态可见和执行日志，避免黑箱化。

---

## 2. 范围边界

### 2.1 V1 包含范围

1. Web 主工作台（收录箱、知识图谱、AI 助手）。
2. 多类型收录与附件解析（文本、链接、图片、文档）。
3. 一键内化与 7 字段结构化笔记生成。
4. 主题/子主题两层知识结构归类与图谱展示。
5. 基于知识库的证据化问答与来源展示。
6. 问答结果回写笔记，形成知识沉淀闭环。
7. 今日提醒与周反馈（快照保存）。
8. 任务状态机、执行日志、失败重试、基础评测样例。

### 2.2 V1 不包含范围

1. 手机端与桌面快捷收录窗。
2. Obsidian 同步/导出。
3. 复杂图谱算法与多层主题体系。
4. 通用聊天机器人能力。
5. 大规模多人协作能力。

## 3. 总体执行策略

### 3.1 产品策略

采用“高保真 UI 骨架优先 + 垂直切片接入”的方式：

1. 先把完整可演示的交互骨架搭起来，确认产品形态正确。
2. 再逐层替换 mock 为真实数据、真实任务、真实 Agent 能力。
3. 全程保持核心路径可演示，避免后期一次性集成风险。

### 3.2 技术策略

采用 Supabase 优先的轻量工程架构：

1. 前端：Next.js + TypeScript。
2. 后端：FastAPI（Agent 编排与任务执行中台）。
3. 数据：Supabase Auth + Postgres + pgvector + Storage。
4. 异步：`jobs` 表 + worker，先不强依赖 Redis/Celery。

### 3.3 Agent 策略

坚持“确定性流程与语义任务分离”：

1. 确定性流程（解析、状态流转、写库、统计）走 Workflow。
2. 需要理解、归纳、判断与生成的环节才交给 Agent。
3. 通过 Orchestrator 统一调度，避免单体“全能 Agent”。

### 3.4 RAG 策略

V1 使用轻量 RAG：

1. 仅向量化 `note_chunks`，不全量向量化原始 `records`。
2. 使用“关键词检索 + 向量检索”的混合召回。
3. 候选结果轻量 rerank 后再回答。
4. 证据不足时必须明确不确定，不允许伪造知识来源。

## 4. 系统架构与职责分层

### 4.1 编排核心

`Workflow Orchestrator` 作为系统中枢，负责：

1. 任务接收与任务路由。
2. Workflow 与 Agent 执行顺序编排。
3. 状态推进、失败重试、超时控制。
4. 幂等保护与关键写入一致性控制。

### 4.2 三个核心 Agent

1. `InternalizationAgent`  
输入：Record 原文 + 用户批注  
输出：7 字段内化草稿 -> 用户确认 -> Note + note_chunks

2. `StructureAgent`  
输入：新 Note  
输出：主题/子主题归类建议 + note_relations + 主题结构建议（不自动落地关键变更）

3. `EvidenceQnAAgent`  
输入：用户问题 + 会话上下文  
输出：基于召回证据的回答 + 来源记录（answer_sources）

### 4.3 三个确定性 Workflow

1. `IngestionWorkflow`：内容接收、类型判断、解析/OCR、快照存储、状态更新。
2. `WritebackWorkflow`：问答价值片段回写、索引刷新、行为记录。
3. `ReminderWorkflow`：日/周统计、候选筛选、提醒与反馈快照生成。

## 5. 统一执行规范（Agent Contract）

为保证可维护性与可观测性，所有 Agent/Workflow 统一执行规范：

1. 标准输入：`task_id`、`user_id`、`object_id`、`context`。
2. 标准输出：`result`、`confidence`、`citations[]`、`decisions[]`。
3. 标准状态：`pending`、`running`、`succeeded`、`failed`、`retrying`、`cancelled`。
4. 标准日志：Prompt 版本、模型、耗时、成本、错误原因、关键中间结果摘要。
5. 标准校验：关键写入前后都要执行完整性校验与幂等校验。

## 6. 分阶段推进计划（非任务清单）

### Phase 0：基础搭建（建议第 1 周）

目标：建立稳定开发底座。

1. 初始化前后端工程。
2. 建立项目目录规范、环境变量规范、API 约定规范。
3. 连接 Supabase 基础能力并完成本地可运行链路。

阶段验收：空壳工程可运行，基础依赖与环境可复现。

### Phase 1：高保真 UI 骨架（建议第 1-2 周）

目标：形成完整可演示产品外壳。

1. 收录箱、详情抽屉、内化草稿抽屉。
2. 知识图谱页面（React Flow mock）。
3. AI 助手页面与提醒弹窗。

阶段验收：基于 mock 数据的端到端交互可演示。

### Phase 2：真实数据接入（建议第 2-3 周）

目标：完成 UI 到数据层切换。

1. 建立核心数据表与基础 RLS。
2. 接入 Auth。
3. 完成 records/attachments/tags/notes 等基础读写。

阶段验收：核心页面可基于真实数据稳定工作。

### Phase 3：任务系统与收录解析闭环（建议第 3-4 周）

目标：构建异步执行骨架与可观测执行链。

1. 落地 `jobs` + worker + 状态流转。
2. 建立 `processing_logs` 执行日志。
3. 打通多类型收录解析流程。

阶段验收：收录后可自动异步解析，失败可追踪可重试。

### Phase 4：内化与知识结构 Agent（建议第 4-5 周）

目标：打通“收录 -> 内化 -> 归类 -> 图谱更新”。

1. 内化 Agent 生成 7 字段草稿并支持用户确认。
2. 写入 note 与 note_chunks，完成向量化。
3. 结构 Agent 完成主题归类与关系生成。

阶段验收：记录可稳定进入“已沉淀”，图谱可反映新增知识。

### Phase 5：RAG 问答与回写（建议第 5-6 周）

目标：形成“可回答、可引用、可沉淀”的复用闭环。

1. 混合召回 + 轻量 rerank。
2. 问答来源记录与证据充分性判断。
3. 高价值回答回写并刷新索引。

阶段验收：问答有来源、证据不足会显式不确定、回写可回流知识库。

### Phase 6：提醒反馈与收尾（建议第 6-8 周）

目标：补齐持续使用闭环与上线前质量保障。

1. 今日提醒、周反馈、历史快照查看。
2. prompt_versions、evaluation_cases、关键日志补齐。
3. 端到端走查、关键异常修复、演示数据准备。

阶段验收：V1 全流程稳定，具备演示与试运行条件。

## 7. 里程碑与质量门禁

### 7.1 里程碑（Gate）

1. Gate A：UI 演示可用（无后端依赖）。
2. Gate B：真实数据可用（Auth + RLS + CRUD）。
3. Gate C：内化闭环可用（收录到沉淀）。
4. Gate D：证据问答可用（来源齐全）。
5. Gate E：提醒反馈与评测可用（具备试运行能力）。

### 7.2 质量门禁（每阶段通用）

1. 功能可走通：主路径至少一条完整 Happy Path。
2. 状态可见：前端状态与任务状态一致可读。
3. 失败可追踪：失败原因可在日志中定位。
4. AI 可解释：输出可追溯到证据与 Prompt 版本。
5. 写入可控：关键操作具备幂等与一致性保证。

## 8. 风险与应对策略

1. 解析质量波动  
应对：原文快照保留、失败重试、用户可修正入口。

2. 内化幻觉或偏差  
应对：强制“原文依据”字段、用户轻确认、记录修改轨迹。

3. 检索召回不稳定  
应对：混合召回 + 轻 rerank 起步，后续按评测样本迭代。

4. 知识结构被自动扰动  
应对：主题合并/拆分仅建议不自动执行，关键变更需用户确认。

5. 模型成本不可控  
应对：按任务分层模型（强/中/轻）+ 成本日志 + 周度复盘。

---

## 9. 执行原则

1. 先闭环后增强：优先保证完整路径可用，而非局部最优。
2. 先可信后智能：证据与可追溯优先于“回答看起来聪明”。
3. 先可观测后扩展：没有日志和评测，不做高风险扩展。
4. 小步快跑：每阶段都保持可演示、可验证、可回滚。
5. 用户负担最小化：用户只做轻确认，不承担复杂知识维护。
