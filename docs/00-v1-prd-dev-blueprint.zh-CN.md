# 个人知识内化 Agent V1

## 1. 文档定位

本文档是 V1 的唯一主文档（single source of truth），统一定义：

1. PRD
2. 页面与功能说明
3. 核心数据模型
4. 流程与状态设计
5. 技术架构
6. 开发阶段与验收标准
7. 已确认与待确认决策

当前 UI 原型参考：

- `E:/my_vibecoding/private_assistant/background-base.html`

原型使用规则：

- `background-base.html` 是 UI 与交互参考基线。
- 它不是最终前端工程架构。
- 在 Phase 1 阶段，前端产物必须与 `background-base.html` 保持 1:1 视觉与交互一致，不允许自行调整布局、信息层级、样式细节或交互路径。
- 组件化、数据接线与结构重构只能在不改变原型呈现结果的前提下进行；若无法同时满足，优先保证原型等价。
- Phase 2 及之后，前端允许为真实逻辑接线调整局部按钮、字段、文案或交互细节，但必须保持整体布局骨架不变。
- 任意会影响用户可见细节的前端改动，必须先征求用户同意，再进入实现。

## 2. 产品目标

构建个人知识内化工作台，帮助用户完成：

1. 收录信息
2. 理解并内化信息
3. 生成可复用笔记
4. 建立轻量知识结构
5. 基于沉淀知识进行有证据问答
6. 将高价值回答回写为新知识

V1 重点是闭环，不是通用聊天机器人。

## 5. 页面与功能说明

### 5.1 收录箱

功能：

1. Quick Capture：支持文字/文档/图片/链接
2. 可选附件上传
3. `我的理解` 输入
4. 收录意图选择：
   - `稍后看`（Later）
   - `收藏`（Favorite，语义为进入待内化）
5. 收录列表筛选与搜索
6. 收录详情抽屉
7. 按状态提供操作：
   - 稍后看：查看原内容、转待内化、一键内化、删除
   - 待内化：查看原内容、一键内化、删除
   - 已沉淀：查看笔记详情、基于笔记提问、定位图谱、删除

### 5.2 知识库

功能：

1. 全局星图展示
2. 缩放与平移
3. 悬浮节点时高亮关联节点
4. 点击节点打开详情并高亮当前节点
5. 在详情页点击关联笔记时，跳转并更新高亮

### 5.3 AI 助手

功能：

1. 用户可随时提问
2. 仅依据已沉淀知识回答
3. 有证据时展示来源
4. 证据不足时明确返回不确定

### 5.4 提醒与周反馈

V1 提供基础 UI 与流程挂钩：

1. 今日提醒
2. 周反馈快照

详细策略可后续迭代。

## 6. 收录与解析规则

### 6.1 收录时用户输入

用户输入：

1. 原始内容：文字/链接/图片/文档
2. 可选附件
3. 可选 `我的理解`
4. 收录意图：`稍后看` 或 `收藏`

收录时不要求用户填写标题。

### 6.2 提交后轻解析

必须完成：

1. 保存原始输入和文件/链接
2. 记录收录时间
3. 识别内容类型
4. 保存来源元信息
5. 保存 `我的理解`
6. 设置用户可见状态

尽力完成：

1. 提取/生成标题
2. 生成预览摘要
3. 自动打标签

标题/摘要/标签可参考：

1. 原始内容
2. 链接可读取的元信息或正文片段
3. 文件元信息或可快速提取文本
4. 用户 `我的理解`

若信息不足无法打标签，显示 `-`。

本阶段不做深度分析：

1. 不做深度价值提取
2. 不做主题归类决策
3. 不做关系图构建
4. 不生成正式笔记
5. 不做图片/视频/文档深度语义理解

### 6.3 收录后可编辑字段

用户可编辑并保存：

1. 标题
2. 预览摘要
3. 标签
4. 我的理解

保存后：

1. 新值覆盖旧值
2. 新值成为最新 canonical record
3. 展示/筛选/搜索/内化均使用最新记录
4. 系统不会因保存自动重新解析

## 7. 内化流程

### 7.1 一键内化模式

V1 采用直接内化：

1. 用户点击一键内化
2. 无草稿审批步骤
3. Agent 直接生成并保存正式笔记
4. 收录状态更新为 `已沉淀`

### 7.2 Agent 输入

内化读取：

1. 原始收录内容
2. 附件
3. 链接快照
4. 用户 `我的理解`
5. 用户编辑后的最新收录字段
6. 已沉淀知识上下文

### 7.3 Agent 输出

正式笔记内容：

1. 标题
2. 核心摘要
3. 关键洞察
4. 可复用方法/结论
5. 适用场景
6. 原文依据

结构输出：

7. 关联笔记建议
8. 主题/子主题归类建议与结构更新

### 7.4 内化后行为

1. 用户可编辑笔记内容
2. V1 用户不可编辑知识结构
3. 结构由 Agent 自动维护

2. 图片：打开图片预览/文件

## 10. 删除规则

采用硬删除，且必须二次确认。

删除已沉淀收录时：

1. 删除收录记录
2. 删除对应正式笔记
3. 联动清理派生与关联数据：
   - note chunks
   - note relations
   - 图谱关联
   - 引用到该笔记的来源关系（按 FK/清理策略）

删除不可恢复。

## 11. AI 助手规则

回答范围：

1. 仅来自已沉淀知识（`notes`、`note_chunks`、关系、主题结构）
2. 不基于未内化收录（`稍后看`/`待内化`）直接回答

证据规则：

1. 有证据必须展示来源
2. 证据不足必须明确不确定
3. 不允许无依据硬答

## 14. 技术架构

已确认技术栈：

1. 前端：Next.js + TypeScript
2. 后端：FastAPI
3. 数据/认证/文件：Supabase Auth + Postgres + Storage
4. 检索向量：pgvector
5. 异步执行：Postgres jobs + worker
6. 模型调用：仅后端统一编排

架构原则：

1. 前端不直连模型
2. 后端集中编排流程
3. AI 输出必须可追溯、可观测
4. V1 基础设施保持轻量、可演进
5. 采用 `Workflow + Multi-Agent` 混合架构：
   - 固定、可规则化步骤由 Workflow 执行
   - 复杂语义理解与生成由 Agent 执行
   - 关键状态推进与数据落库由 Workflow 统一控制

### 14.1 Agent 角色（V1）

1. `CaptureParsingAgent`：负责标题/摘要/标签轻语义补全。
2. `InternalizationAgent`：负责正式可复用笔记内容生成。
3. `StructureAgent`：负责主题/子主题归类与关联建议。
4. `EvidenceQnAAgent`：负责证据化回答、来源与不确定性表达。
5. `Workflow Orchestrator`：负责路由、状态机、重试、超时、审计与落库。

### 14.2 Workflow 与 Agent 分工（V1）

1. 收录流程：Workflow 负责保存、状态、日志；Agent 负责标题/摘要/标签补全。
2. 内化流程：Workflow 负责编排与写库；Agent 负责笔记生成与结构判断。
3. 问答流程：Workflow 负责检索与分支；Agent 负责组织证据化回答。
4. 删除流程：Workflow 独立执行二次确认与级联硬删除；Agent 不参与。
5. 提醒反馈：Workflow 先统计事实数据，Agent 生成行动建议，Workflow 再保存与发布。

### 14.3 提醒反馈规则（V1）

1. 今日/周数据统计必须由 Workflow 生成。
2. Agent 只基于统计事实生成总结与建议，不生成原始事实数据。
3. 最终展示内容由 Workflow 统一校验和落库。

### 14.4 冻结执行计划（全程按此推进）

1. Phase 0：工程底座（前后端骨架、配置、Supabase、健康检查）。
2. Phase 1：原型迁移（将 `background-base.html` 迁移为 Next.js 页面组件）。
3. Phase 2：收录真实化（records/attachments/jobs/logs 替换 mock）。
4. Phase 3：内化闭环（一键内化 -> notes/note_chunks -> 已沉淀）。
5. Phase 4：知识库真实化（topics/subtopics/relations + 图谱联动）。
6. Phase 5：AI 助手与检索（来源展示、证据不足不确定、回答回写）。
7. Phase 6：提醒反馈与质量门禁（日周反馈闭环、评测与灰度）。

执行约束：

1. 默认严格按上述顺序推进。
2. 如需变更，先更新本文档再改代码。
3. 每阶段完成后必须追加进度日志。

## 16. 验收标准

产品验收：

1. 用户可完成 收录 -> 内化 -> 图谱定位 -> 基于笔记问答 全链路
2. 主链路无需人工修数据即可跑通

数据验收：

1. 收录与笔记生命周期一致
2. 硬删除清理完整且可预期

AI 验收：

1. 有证据必有来源展示
2. 证据不足必显式不确定

可观测性验收：

1. 任务状态与失败原因可追踪
2. 处理日志可查询可诊断

## 17. 已确认决策

### Decision-001：HTML 原型定位

已确认：

- `background-base.html` 是 UI 与交互参考。
- 不是最终前端架构。
- Phase 1 必须先做到与原型完全一致，再讨论后续结构性重构。

### Decision-002：V1 技术栈

已确认：

1. Next.js + TypeScript
2. FastAPI
3. Supabase Auth + Postgres + Storage
4. pgvector
5. Postgres jobs + worker
6. 后端统一模型编排

### Decision-003：`收藏` 的含义

已确认：

- `收藏` 表示高价值、应进入待内化。
- 不等于已沉淀。

### Decision-004：收录后解析范围

已确认：

1. 仅轻解析
2. 深度理解放到一键内化
3. 标题/摘要/标签可参考 `我的理解`
4. 信息不足时标签显示 `-`

### Decision-005：收录后可编辑字段

已确认：

1. 标题/摘要/标签/我的理解可编辑
2. 用户保存后覆盖旧值并成为最新 canonical record

### Decision-006：用户保存后是否自动重解析

已确认：

- 不自动重解析

### Decision-007：内化输出结构

已确认：

1. 正式笔记包含 6 个核心内容字段
2. 结构输出包含关联与主题归类

### Decision-008：一键内化与结构归属

已确认：

1. 无内化前人工审核步骤
2. 用户可编辑笔记内容
3. V1 用户不可编辑结构
4. 结构由 Agent 维护

### Decision-009：AI 助手回答范围

已确认：

- 仅使用已沉淀知识回答

### Decision-010：原内容与快照策略

已确认：

- 链接保存基础快照，不做完整离线归档

### Decision-011：图谱实现策略

已确认：

1. 先锁定产品行为

### Decision-012：删除已沉淀内容规则

已确认：

- 删除已沉淀收录时，同步删除对应笔记及关联派生数据

### Decision-013：删除模式

已确认：

1. 硬删除
2. 必须二次确认
3. 不可恢复

### Decision-014：来源与不确定性

已确认：

1. 有证据必须显示来源
2. 证据不足必须明确不确定

### Decision-015：架构冻结原则

已确认：

1. V1 采用 `Workflow-Orchestrated Multi-Agent`。
2. 简单固定工作交给 Workflow，复杂语义工作交给 Agent。
