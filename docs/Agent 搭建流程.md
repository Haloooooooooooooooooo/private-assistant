# Agent 搭建流程

# 1. 先定义产品闭环，而不是先定义功能

你现在最核心的闭环不是“做一个知识库”，而是：

**用户把资料丢进去 → 系统判断状态 → AI 内化成结构化笔记 → AI 归入知识结构 → 用户轻确认 → 以后可以基于知识库问答 → 问答结果还能回写到笔记里。**

这才是你的产品主线。

你文档里的三个状态「稍后看 / 待内化 / 已沉淀」非常重要，因为它们天然就是 Agent 的任务状态机。

面试时你可以这样说：

> 我没有先堆功能，而是先定义知识内化的生命周期。每条内容进入系统后，不是简单保存，而是会经历稍后看、待内化、已沉淀三个状态。Agent 的职责就是推动内容从原始资料变成可复用知识，同时保证用户可以轻确认、可追溯、可修改。

这比单纯说“我做了收录、标签、问答”高级很多。

------

# 2. 拆 Agent 工作流，但要按你的业务链路拆

别人给你的“拆 Agent 工作流”是对的，但你不能抽象地拆。你要按你的产品拆成 5 条 Agent 工作流。

### 工作流 1：收录 Agent

负责处理用户输入的原始内容。

输入包括：

文本、链接、图片、PDF、docx、md、txt、本地文件、剪贴板图片。

你文档里已经定义了 V1 支持 pdf、docx、md、txt、png、jpg、jpeg、webp，不支持 xls、ppt、zip，并且不支持时要保留记录和标记原因。

它要做的事情是：

识别内容类型，提取正文，生成标题，识别来源，保存原始快照，判断是否可解析，打上异常标记。

这一步的重点不是“智能”，而是**稳定、低摩擦、可追溯**。

------

### 工作流 2：内化 Agent

负责把原始内容转成结构化笔记。

你文档中已经明确“一键内化”会生成 7 字段草稿，然后用户轻确认/微调并保存。

这里你要把 7 字段固定下来，比如：

1. 核心观点
2. 关键概念
3. 我的理解
4. 可复用结论
5. 使用场景
6. 相关问题
7. 原文依据

这个 Agent 的重点是：**不是总结，而是把内容变成未来可复用的知识。**

面试时你可以说：

> 我把“总结”和“内化”区分开。总结只是压缩内容，内化是把内容转成用户未来能调用的知识单元，所以我会要求模型输出核心观点、可复用结论、使用场景、相关问题和原文依据。

------

### 工作流 3：知识结构 Agent

负责把笔记放进知识库。

你的设计里很关键的一点是：V1 不让用户手动搭复杂知识体系，而是由 AI 自动新增、合并、拆分主题结构，用户只保留重命名能力。

这其实就是一个 Agent 能力点。

它要判断：

这条笔记属于哪个主题？
是否需要创建新子主题？
是否和已有笔记有关系？
关系是补充、对比、延伸、反例，还是应用？
是否需要合并相似主题？
是否存在主题漂移？

你这里的设计很适合面试，因为它体现了你对 AI 产品的一个核心判断：

> 不让用户维护复杂结构，而是让 AI 维护结构，用户只做轻确认。

这就是你的差异化。

------

### 工作流 4：知识问答 Agent

负责基于知识库回答问题。

你文档里已经限定：AI 助手只做知识问答，不做通用闲聊，并且每条回答必须附参考记录，无充分依据时要明确不确定。

这一步很重要，因为它决定你的 Agent 不是普通聊天机器人，而是一个**证据化知识助手**。

它要做：

理解问题 → 检索相关笔记 → 判断证据是否足够 → 组织回答 → 附上来源 → 标明不确定性 → 支持加入笔记。

面试时你可以说：

> 我会把 AI 助手限制在用户知识库范围内，不做开放式闲聊。回答必须带引用记录，避免模型把通用知识和用户知识混在一起。没有依据时，Agent 要显式拒答或提示不确定。

------

### 工作流 5：回写沉淀 Agent

这是你设计里很有价值的一环。

你文档里写到，每条助手回答支持「加入笔记」，并回写到固定区块「小助手对话沉淀」，包括原问题、规范化问题、助手回答和时间。

这个设计很重要，因为它让问答不是一次性消费，而是继续反哺知识库。

面试时可以这样说：

> 我不希望 AI 问答只是即时回答，所以设计了回写机制。用户觉得某次回答有价值，可以一键加入原笔记，系统会保存原问题、规范化问题、回答和时间，让知识库随着使用不断变厚。

------

# 3. 设计输入、输出和状态：你要做成 Agent 状态机

你原来那一步“设计输入、输出和状态”非常适合你，但要更具体。

你每条记录至少要有这些状态：

```text
原始收录
↓
解析中
↓
解析成功 / 解析失败
↓
稍后看 / 待内化
↓
内化中
↓
内化草稿
↓
用户确认
↓
已沉淀
↓
可问答 / 可回写 / 可关联
```

你现在用户可见状态只保留三个，这很好：

```text
稍后看
待内化
已沉淀
```

但是系统内部要有更多状态，比如：

```text
uploaded
parsing
parse_failed
parsed
pending_internalization
internalizing
draft_generated
confirmed
embedded
linked
answered
written_back
```

这就是面试里可以讲的“产品状态”和“系统状态”的区别。

你可以这样说：

> 用户侧我只暴露三个简单状态，降低理解成本；系统侧我会保留更细的处理状态，用于任务恢复、失败重试、日志追踪和评测分析。这样既能保持产品简单，又能让 Agent 工程可维护。

------

# 4. 设计 Agent 架构：你适合用“多模块 Agent”，不是一个大 Agent

你的产品不适合做成一个超级 Agent，一次性处理所有事情。

更适合这样：

```text
前端收录层
  ↓
任务队列 / 状态管理
  ↓
内容解析服务
  ↓
内化 Agent
  ↓
结构整理 Agent
  ↓
向量检索 / 知识库
  ↓
问答 Agent
  ↓
回写 Agent
```

你可以把 Agent 架构说成 4 层：

## 第一层：输入层

负责接收用户资料。

包括：

Web 主工作台、桌面快捷收录窗、文件上传、链接粘贴、图片粘贴。

你的文档里已经明确电脑端采用 Web 主工作台 + 桌面快捷收录窗的混合形态。

## 第二层：处理层

负责解析和清洗内容。

包括：

OCR、文档解析、网页正文提取、异常标记、原始快照保存。

## 第三层：Agent 层

负责智能任务。

包括：

内化 Agent、主题归类 Agent、关联发现 Agent、问答 Agent、回写 Agent。

## 第四层：知识层

负责存储和检索。

包括：

原始内容库、结构化笔记库、主题结构、标签、向量索引、关系图谱、对话沉淀。

------

# 5. 准备 Codex 开发说明：你不能只写“帮我开发”

你要给 Codex 的不是一句需求，而是分阶段开发说明。

建议你准备 5 类文档：

## 1. 产品说明文档

说明这个产品解决什么问题、核心闭环是什么、V1 边界是什么。

你现在这份页面设计稿就可以作为基础。

## 2. 页面结构说明

把页面拆成：

收录箱
知识库
AI 助手
详情抽屉
内化抽屉
追问抽屉
桌面快捷收录窗

每个页面写清楚：

展示什么
可以操作什么
操作后状态怎么变化
和 Agent 怎么交互

## 3. 数据结构说明

你至少要定义这些对象：

```text
Record 原始记录
Note 内化笔记
Topic 主题
SubTopic 子主题
Tag 标签
Relation 笔记关系
Conversation AI 对话
AnswerSource 回答引用
Attachment 附件
ProcessingLog 处理日志
EvaluationCase 评测样例
```

这一步非常重要。你要低迭代成本，就必须先把数据结构想清楚。

## 4. Agent Prompt 说明

不要只写一个 prompt。

你应该拆成：

收录解析 Prompt
内化 Prompt
主题归类 Prompt
关联发现 Prompt
问答 Prompt
不确定性判断 Prompt
回写 Prompt

## 5. 评测说明

从第一版开始就保留评测数据，而不是等产品做好后再评测。

# 6. vibecoding 分阶段实现：你应该这样做

你不是不做 MVP，而是做一个**带完整架构意识的 MVP**。

也就是：功能可以少，但结构不能乱。

## 阶段 1：先做“收录 → 内化 → 已沉淀”的闭环

先不要急着做复杂图谱。

实现：

快速添加
记录列表
三个状态
详情抽屉
一键内化
7 字段草稿
用户保存
已沉淀笔记

这是你的最小闭环。

这一步完成后，你就有了一个可以演示的 Agent：

> 用户输入一条资料，Agent 自动生成可复用笔记，用户确认后进入知识库。

------

## 阶段 2：做知识库结构

实现：

主题
子主题
笔记归属
AI 自动归类
用户重命名主题
笔记详情
原文快照

先不用做很炫的图谱，可以先用简单树状结构或卡片结构代替。

等逻辑稳定后，再做图谱主视图。

------

## 阶段 3：做证据化问答

实现：

用户提问
检索相关笔记
回答
附参考记录
无依据时提示不确定
基于某条笔记追问

这是你的 Agent 最重要的能力之一。

------

## 阶段 4：做回写沉淀

实现：

加入笔记
保存原问题
保存规范化问题
保存回答
保存时间
支持编辑和删除

这一步能体现你的产品不是普通 RAG，而是“知识越用越沉淀”。

------

## 阶段 5：做桌面快捷收录窗

这个可以稍后做。

因为它是体验增强，不是 Agent 核心能力。

你文档里也写了，桌面快捷收录窗只做快速收录和状态选择，不承担管理与深度编辑。

# 7. 建立评测体系：这是你面试最应该讲好的部分

你的评测不能只测“回答对不对”。

你要按 Agent 工作流分层评测。

## 评测 1：解析质量

看系统能不能正确处理不同输入。

测试样例：

文本
链接
截图
PDF
docx
md
txt
不支持文件
低质量图片
重复内容

评测指标：

是否成功提取正文
标题是否合理
来源是否识别正确
失败原因是否明确
是否保存原始快照
是否误删信息

------

## 评测 2：内化质量

看 Agent 生成的笔记有没有价值。

评测指标：

是否抓住核心观点
是否没有编造
是否能提炼可复用结论
是否结合了用户批注
是否保留原文依据
是否适合未来检索
是否结构稳定

你可以设计一个 1-5 分人工评分表：

```text
准确性：1-5
完整性：1-5
可复用性：1-5
结构清晰度：1-5
个性化程度：1-5
无幻觉程度：1-5
```

------

## 评测 3：主题归类质量

看知识结构 Agent 是否稳定。

评测指标：

是否归到正确主题
是否创建了不必要的新主题
是否把不同概念混在一起
是否能发现相关笔记
关系类型是否准确
主题是否越来越乱

这里非常适合做失败案例分析。

比如：

```text
失败案例：模型把“Agent 评测”归到了“产品设计”，但更应该归到“AI 工程化”。
原因：主题定义不清。
优化方式：给每个主题增加主题说明和代表笔记。
```

------

## 评测 4：问答质量

看 AI 助手能不能基于知识库回答。

评测指标：

是否检索到正确笔记
是否引用了来源
是否回答了问题
是否没有超出知识库乱说
证据不足时是否说明不确定
多轮追问是否保持上下文

你可以把问题分成几类：

```text
事实查找类：我之前记录过什么？
总结归纳类：帮我总结我对 Agent 的理解。
对比分析类：我的产品和 Obsidian 有什么区别？
决策建议类：我下一步应该先做什么？
追问扩展类：基于这条笔记继续问。
```

------

## 评测 5：回写质量

看有价值的问答能不能沉淀回知识库。

评测指标：

是否写入正确笔记
是否保留原问题
是否生成规范化问题
是否保留回答时间
是否没有污染原笔记
是否方便以后再次检索

------

# 8. Prompt 优化：你要按失败类型优化，而不是凭感觉改

你后续优化 Prompt 时，不要看到结果不好就随便改。

你应该建立一个失败案例表：

```text
失败 ID
输入内容
期望输出
实际输出
失败类型
失败原因
优化方式
优化后结果
```

失败类型可以分为：

```text
解析失败
总结太泛
没有结合我的理解
编造内容
主题归类错误
重复创建主题
关系类型错误
检索不到相关笔记
回答没有引用
证据不足却强答
回写位置错误
```

然后对应优化：

如果总结太泛：加强输出字段和示例。
如果编造内容：要求只基于原文和用户批注。
如果主题归类错误：增加主题定义和已有主题候选。
如果重复创建主题：要求优先匹配已有主题，只有明显不匹配才新建。
如果回答无依据：增加证据阈值和拒答规则。
如果回写污染笔记：固定回写区块，不允许覆盖原内容。

面试时你可以说：

> 我不会凭感觉调 Prompt，而是先沉淀失败案例，把失败归因到解析、内化、归类、检索、回答、回写等环节，再针对性修改 Prompt、检索策略或数据结构。

------

# 9. 模型选型优化：你可以按任务分模型，不要所有任务都用最贵模型

你的产品很适合做“任务分级模型选型”。

## 可以用轻模型的任务

标题生成
标签建议
状态判断
简单摘要
重复检测
搜索联想

这些任务成本敏感、容错率高。

## 应该用强模型的任务

深度内化
主题结构调整
复杂问答
多笔记综合分析
失败案例归因
Prompt 自动优化建议

这些任务对质量要求更高。

## 可以用非 LLM 的任务

文件类型判断
状态流转
向量检索
关键词搜索
去重
时间筛选
附件解析

面试时你可以说：

> 我不会所有环节都调用大模型。V1 会先用一个稳定模型跑通闭环，后续再按任务拆分：低风险任务用轻模型，高价值任务用强模型，确定性任务尽量不用模型，降低成本和延迟。

------

# 10. 日志和持续优化：你要从一开始就保留这些信息

你说“我希望让 AI 帮我意识到并且保留下来”，这个想法非常对。

你需要保留的不只是用户内容，还包括 Agent 运行过程。

每次 Agent 执行都应该记录：

```text
任务类型
输入内容
使用的 Prompt 版本
使用的模型
检索到的笔记
输出结果
用户是否修改
用户是否保存
用户是否删除
失败原因
耗时
成本
```

这些日志后面可以用来做：

Prompt 优化
模型对比
评测集构建
失败案例复盘
用户行为分析
功能优先级判断

面试时你可以说：

> 我会把用户修改行为当作高价值反馈。比如用户频繁修改某个字段，说明该字段 Prompt 不稳定；用户经常删除某类生成结果，说明内化策略或主题归类有问题。这些都会进入后续优化闭环。


# 最后给你一个面试表达版本

你可以这样讲你的 Agent 搭建思路：

> 我的项目不是一个普通收藏夹，也不是单纯的 RAG 问答工具，而是一个个人知识内化 Agent。
>
> 我先定义了完整闭环：用户低摩擦收录资料，系统解析内容并生成结构化内化笔记，再自动归入知识库主题结构。之后用户可以基于自己的知识库进行证据化问答，回答结果如果有价值，还可以回写到原笔记中，形成持续沉淀。
>
> 在 Agent 设计上，我不会做一个大而全的 Agent，而是拆成收录解析、内容内化、知识结构整理、证据化问答和回写沉淀几个工作流。每个工作流都有明确输入、输出、状态和失败处理。
>
> 在产品设计上，我会让用户侧保持简单，只看到稍后看、待内化、已沉淀三个状态；但系统侧会保留更细的解析中、解析失败、内化中、草稿生成、已确认、已嵌入、已回写等状态，用来支持任务恢复、日志追踪和持续优化。
>
> 在优化上，我会从第一版开始建立评测体系，不只评估问答准确率，还会分别评估解析质量、内化质量、主题归类质量、证据化问答质量和回写质量。后续根据用户修改、失败案例和运行日志，持续优化 Prompt、检索策略和模型选型。
>
> 我的目标不是一次性做完所有功能，而是先保证核心闭环跑通，同时让数据结构、状态流转和评测体系具备连续迭代能力，这样后续加图谱、桌面快捷窗、多端收录时，迭代成本会比较低。

这套思路很适合你现在的方向。你现在下一步不是继续加功能，而是把这份页面设计稿继续升级成一份**Agent 工程设计文档**：包括工作流、数据结构、状态机、Prompt、评测集和分阶段开发计划。
